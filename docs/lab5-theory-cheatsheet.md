# Краткая теория к лабораторной работе 5

## 1. Bulk-операции

**Bulk-операция** — это операция, которая обрабатывает сразу несколько объектов за один вызов.

**Зачем нужна** — уменьшает число отдельных запросов, упрощает массовое создание, обновление или удаление данных.

**Типичный пример** — `POST`-запрос, в теле которого передаётся массив объектов.

**Что важно учитывать** — размер запроса, обработку ошибок и транзакционность всей операции.

## 2. Stream API

**Stream API** — это механизм декларативной обработки последовательности элементов.

**Главная идея** — не писать цикл вручную, а описывать цепочку операций над данными.

**Когда используется** — для фильтрации, преобразования, сортировки и сборки коллекций.

### Основные операции Stream API

**Промежуточные операции** — это операции, которые преобразуют поток и возвращают новый `Stream` для дальнейшей обработки.

**Терминальные операции** — это операции, которые завершают обработку потока и дают итоговый результат или побочный эффект.

**`stream()`** — создаёт поток элементов из коллекции.

**`map()`** — промежуточная операция; преобразует каждый элемент в другой объект.

**`filter()`** — промежуточная операция; оставляет только элементы, которые подходят под условие.

**`sorted()`** — промежуточная операция; сортирует элементы.

**`forEach()`** — терминальная операция; выполняет действие для каждого элемента.

**`toList()`** — терминальная операция; собирает результат обратно в список.

**`collect(...)`** — терминальная операция; собирает результат в нужную структуру, например в `List`, `Set` или `Map`.

## 3. Лямбда-выражения

**Лямбда-выражение** — это краткая запись анонимной функции.

**Зачем нужно** — позволяет передавать поведение как аргумент и писать короче код, особенно вместе со `Stream API`.

**Функциональный интерфейс** — это интерфейс, у которого есть ровно один абстрактный метод.

**Связь с лямбдой** — лямбда-выражение может использоваться как реализация функционального интерфейса.

**Главная идея** — вместо создания отдельного анонимного класса можно сразу передать реализацию единственного метода в короткой форме.

**Пример**:

```java
user -> user.getName()
```

**Смысл примера** — для объекта `user` вернуть его имя.

## 4. Optional

**Optional<T>** — это контейнер, который либо содержит значение, либо пуст.

**Зачем нужен** — позволяет явно показать, что значение может отсутствовать, и уменьшает количество прямых проверок на `null`.

### Основные операции Optional

**`of(...)`** — создаёт `Optional` из гарантированно непустого значения.

**`ofNullable(...)`** — создаёт `Optional`, где значение может быть `null`.

**`map(...)`** — преобразует значение, если оно есть.

**`filter(...)`** — оставляет значение только при выполнении условия.

**`orElse(...)`** — возвращает значение по умолчанию, если `Optional` пуст.

**`orElseThrow(...)`** — выбрасывает исключение, если значения нет.

## 5. Пирамида тестирования

**Пирамида тестирования** — это модель распределения тестов по уровням.

**Нижний уровень** — unit-тесты; их должно быть больше всего.

**Следующий уровень** — integration tests; их обычно меньше.

**Выше** — system tests; они проверяют систему крупными сценариями.

**Верхний уровень** — end-to-end тесты; их обычно меньше всего.

**Смысл пирамиды** — большинство проверок должны быть быстрыми, дешёвыми и изолированными.

### Уровни пирамиды

**Unit testing** — проверка отдельного класса или метода в изоляции от внешних зависимостей.

**Integration testing** — проверка совместной работы нескольких компонентов, например сервиса, репозитория и базы данных.

**System testing** — проверка всей системы как единого приложения по крупным функциональным сценариям.

**E2E testing** — проверка полного пользовательского сценария от входа в систему до получения конечного результата.

### Идея пирамиды

**Unit-тесты** — самые быстрые, самые дешёвые и самые изолированные.

**Integration-тесты** — медленнее unit-тестов, но проверяют реальные связи между компонентами.

**System-тесты** — ещё ближе к реальной работе приложения, но тяжелее в запуске и поддержке.

**E2E-тесты** — самые дорогие и медленные, поэтому их должно быть меньше всего.

## 6. TDD

**TDD** (`Test-Driven Development`) — это подход, при котором сначала пишется тест, а потом код под него.

**Классический цикл TDD**:

1. написать тест;
2. убедиться, что он падает;
3. написать минимальный код, чтобы тест прошёл;
4. выполнить рефакторинг.

**Короткая формула TDD** — `Red -> Green -> Refactor`.

## 7. Unit-тесты

**Unit-тест** — это тест, который проверяет небольшую единицу логики изолированно от внешних зависимостей.

**Обычно проверяет** — один класс, один метод или одну бизнес-ветку.

**Плюсы** — быстрый запуск, простая диагностика ошибок, низкая стоимость поддержки.

## 8. Интеграционные тесты

**Интеграционный тест** — это тест, который проверяет совместную работу нескольких компонентов системы.

**Обычно включает** — Spring-контекст, базу данных, репозитории, HTTP-слой или реальные конфигурации.

**Главная цель** — убедиться, что компоненты правильно работают вместе, а не только по отдельности.

## 9. Unit vs интеграционные тесты

**Unit-тест** — изолированный, быстрый, обычно использует моки.

**Интеграционный тест** — проверяет взаимодействие компонентов, работает медленнее и ближе к реальному запуску приложения.

**Идея различия** — unit-тест отвечает на вопрос «правильно ли работает этот кусок логики?», а интеграционный — «правильно ли взаимодействуют части системы друг с другом?».

## 10. JUnit

**JUnit** — это фреймворк для написания и запуска тестов в Java.

**Что даёт JUnit** — аннотации тестов, проверки результатов и механизм запуска тестовых сценариев.

### Часто используемые элементы JUnit

**`@Test`** — помечает метод как тест.

**`assertEquals`** — проверяет равенство ожидаемого и фактического значения.

**`assertTrue`** — проверяет, что условие истинно.

**`assertThrows`** — проверяет, что код выбрасывает ожидаемое исключение.

## 11. Mockito

**Mockito** — это библиотека для создания mock-объектов в unit-тестах.

**Mock** — это подставной объект, который имитирует поведение реальной зависимости.

**Зачем нужен Mockito** — чтобы изолировать тестируемый класс от базы данных, внешних сервисов и других зависимостей.

### Часто используемые элементы Mockito

**`@Mock`** — создаёт mock-объект.

**`@InjectMocks`** — создаёт тестируемый объект и подставляет в него моки.

**`when(...).thenReturn(...)`** — задаёт поведение mock-объекта.

**`verify(...)`** — проверяет, что у mock-объекта был вызван нужный метод.
