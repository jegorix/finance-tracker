# Краткая теория к лабораторной работе 6

## 1. Потоки и процессы

**Процесс** — это экземпляр запущенной программы со своей памятью, ресурсами и состоянием выполнения.

**Поток** — это отдельная линия выполнения внутри процесса.

**Главное различие** — процессы изолированы друг от друга сильнее, а потоки одного процесса работают в общем адресном пространстве.

**Что это значит на практике** — потоки быстрее создавать и переключать, чем процессы, но при этом им требуется аккуратная синхронизация.

**У процесса есть** — собственная память, дескрипторы файлов, системные ресурсы.

**У потока есть** — свой стек выполнения, но общие с другими потоками данные процесса.

**Зачем нужны потоки** — для параллельного выполнения задач, фоновой обработки, асинхронных операций и более эффективного использования ресурсов процессора.

## 2. Race condition

**Race condition** — это ситуация, когда результат работы программы зависит от непредсказуемого порядка выполнения потоков.

**Когда возникает** — когда несколько потоков одновременно читают и изменяют общие данные без корректной синхронизации.

**Главная проблема** — программа может иногда работать правильно, а иногда давать неправильный результат.

**Типичный пример** — два потока одновременно увеличивают общий счётчик, и часть обновлений теряется.

```java
counter++;
```

**Почему это опасно** — операция увеличения не является атомарной; она состоит из чтения, вычисления и записи.

**Как решается** — с помощью `synchronized`, `AtomicInteger`, `Lock` и других механизмов синхронизации.

## 3. Deadlock

**Deadlock** — это взаимная блокировка, при которой два или более потока навсегда ждут друг друга и не могут продолжить работу.

**Простой пример**:

- поток 1 захватил ресурс A и ждёт ресурс B;
- поток 2 захватил ресурс B и ждёт ресурс A.

**Результат** — оба потока зависают.

### Условия возникновения deadlock

**Взаимное исключение** — ресурс нельзя использовать одновременно из нескольких потоков.

**Удержание и ожидание** — поток уже держит один ресурс и ждёт другой.

**Отсутствие принудительного освобождения** — ресурс нельзя отобрать у потока извне.

**Циклическое ожидание** — потоки образуют замкнутую цепочку ожидания ресурсов.

### Как уменьшить риск deadlock

**Единый порядок захвата блокировок** — все потоки должны брать ресурсы в одинаковом порядке.

**Минимизация времени удержания блокировки** — чем короче критическая секция, тем меньше риск.

**Использование таймаутов** — иногда лучше прервать ожидание, чем ждать бесконечно.

## 4. Создание потока

**Создание потока** — это запуск отдельного потока выполнения для параллельной работы кода.

### Основные способы в Java

**Наследование от `Thread`** — создаётся класс-потомок, который переопределяет метод `run()`.

```java
class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("Thread is running");
    }
}
```

**Реализация `Runnable`** — логика потока выносится в объект, который передаётся в `Thread`.

```java
Runnable task = () -> System.out.println("Thread is running");
new Thread(task).start();
```

**Использование `ExecutorService`** — современный и более удобный способ управления пулом потоков.

```java
ExecutorService executor = Executors.newFixedThreadPool(4);
executor.submit(() -> System.out.println("Task"));
executor.shutdown();
```

**Почему `ExecutorService` предпочтительнее** — он позволяет переиспользовать потоки, ограничивать их число и централизованно управлять задачами.

## 5. `volatile`

**`volatile`** — это модификатор поля, который гарантирует видимость последнего записанного значения между потоками.

**Главная идея** — если один поток изменил `volatile`-поле, другой поток увидит актуальное значение.

**Что `volatile` решает** — проблему видимости.

**Чего `volatile` не решает** — проблему атомарности составных операций.

**Пример**:

```java
private volatile boolean running = true;
```

**Когда подходит** — для флагов остановки, признаков состояния и других простых случаев чтения-записи.

**Когда не подходит** — для `counter++`, балансов, сложных обновлений и другой составной логики.

## 6. `synchronized`

**`synchronized`** — это встроенный механизм синхронизации в Java, который позволяет ограничить доступ к критической секции одним потоком за раз.

**Что даёт**:

- взаимное исключение;
- упорядоченность доступа;
- корректную видимость данных между потоками.

**Пример синхронизированного метода**:

```java
public synchronized void increment() {
    counter++;
}
```

**Критическая секция** — участок кода, где происходит работа с общими данными и где особенно важно избежать одновременного доступа.

**Плюс `synchronized`** — простой и надёжный способ защитить общий ресурс.

**Минус `synchronized`** — при избыточном использовании может снижать производительность и усложнять конкурентное выполнение.

## 7. `CompletableFuture`

**`CompletableFuture`** — это класс в Java для асинхронного выполнения задач и построения цепочек обработки результата.

**Главная идея** — задача запускается в фоне, а результат можно получить позже или обработать следующими шагами.

**Что умеет `CompletableFuture`**:

- запускать асинхронную задачу;
- объединять несколько задач;
- обрабатывать успешный результат;
- обрабатывать ошибки;
- строить цепочки асинхронных операций.

### Часто используемые методы

**`runAsync(...)`** — запускает асинхронную задачу без возвращаемого результата.

**`supplyAsync(...)`** — запускает асинхронную задачу, которая возвращает результат.

**`thenApply(...)`** — преобразует результат предыдущего шага.

**`thenAccept(...)`** — получает результат и выполняет действие без нового значения.

**`thenCompose(...)`** — связывает две асинхронные операции последовательно.

**`allOf(...)`** — ждёт завершения нескольких `CompletableFuture`.

**`exceptionally(...)`** — задаёт обработку ошибки.

### Пример

```java
CompletableFuture.supplyAsync(() -> "data")
        .thenApply(String::toUpperCase)
        .thenAccept(System.out::println);
```

**Где особенно полезен** — в асинхронных сервисах, параллельной обработке и сценариях, где не хочется блокировать основной поток.

## 8. Нагрузочное тестирование

**Нагрузочное тестирование** — это проверка поведения системы под заданным количеством запросов, пользователей или операций.

**Главная цель** — понять, как приложение ведёт себя при росте нагрузки.

### Что обычно проверяют

**Время ответа** — как быстро система отвечает на запрос.

**Пропускную способность** — сколько запросов система может обработать за единицу времени.

**Стабильность** — появляются ли ошибки при увеличении нагрузки.

**Пределы системы** — в какой момент начинается деградация производительности.

### Основные виды

**Load testing** — обычная рабочая нагрузка.

**Stress testing** — нагрузка выше нормальной, чтобы найти предел.

**Spike testing** — резкий скачок нагрузки.

**Endurance testing** — длительная нагрузка, чтобы проверить устойчивость во времени.

### JMeter

**JMeter** — популярный инструмент для нагрузочного тестирования HTTP-сервисов.

**Что позволяет делать** — запускать много виртуальных пользователей, настраивать количество потоков, циклы, время разгона и собирать метрики.

**Важные метрики в JMeter**:

- `Average` — среднее время ответа;
- `Throughput` — число запросов за единицу времени;
- `Error %` — процент ошибок;
- `95% Line` или `95th percentile` — значение, в которое укладывается 95% запросов.

## 9. RateLimiter

**RateLimiter** — это механизм ограничения частоты запросов или операций.

**Главная задача** — не дать клиенту, пользователю или сервису выполнять слишком много запросов за короткое время.

**Зачем нужен**:

- защита от перегрузки;
- защита от злоупотребления API;
- более справедливое распределение ресурсов;
- снижение риска атак типа brute force или flood.

### Как работает в общем виде

**Идея** — системе задают лимит, например не более `100` запросов в минуту.

**Если лимит превышен** — новые запросы отклоняются, откладываются или замедляются.

### Популярные алгоритмы

**Fixed Window** — считает запросы в фиксированном временном окне.

**Sliding Window** — считает запросы в скользящем окне и обычно даёт более точный результат.

**Token Bucket** — запрос можно выполнить, если в “ведре” есть токен; токены пополняются со временем.

**Leaky Bucket** — запросы вытекают с фиксированной скоростью, сглаживая пики нагрузки.

## 10. ELK стек

**ELK стек** — это набор инструментов для централизованного сбора, хранения, поиска и визуализации логов.

**ELK** расшифровывается так:

- `Elasticsearch`
- `Logstash`
- `Kibana`

### Компоненты ELK

**Elasticsearch** — система хранения и быстрого поиска данных.

**Logstash** — инструмент для приёма, преобразования и маршрутизации логов.

**Kibana** — веб-интерфейс для поиска, фильтрации и визуализации логов.

### Для чего нужен ELK

**Централизация логов** — логи разных сервисов собираются в одном месте.

**Быстрый поиск ошибок** — можно искать по времени, уровню логирования, тексту сообщения и другим полям.

**Мониторинг и анализ** — можно строить дашборды, графики и отслеживать аномалии.

**Разбор инцидентов** — удобно анализировать сбои, ошибки и поведение системы под нагрузкой.
