# Теория к лабораторной работе 4

## 1. Проверяемые и непроверяемые исключения

### Проверяемые исключения

Проверяемые исключения (`checked exceptions`) наследуются от `Exception`, но не от `RuntimeException`.

Их особенность в том, что компилятор требует либо обработать исключение через `try/catch`, либо указать его в `throws`.

Обычно такие исключения используют там, где возможен внешний сбой:

- работа с файлами;
- сеть;
- база данных;
- ввод-вывод.

Примеры:

- `IOException`
- `SQLException`

### Непроверяемые исключения

Непроверяемые исключения (`unchecked exceptions`) наследуются от `RuntimeException`.

Компилятор не заставляет обрабатывать их явно. Чаще всего они показывают ошибку логики, некорректные данные или нарушение бизнес-правил.

Примеры:

- `NullPointerException`
- `IllegalArgumentException`
- `IllegalStateException`

### Когда что использовать

- `checked` подходят для ожидаемых внешних ошибок;
- `unchecked` удобны для ошибок программирования и бизнес-ошибок.

В Spring-приложениях бизнес-исключения часто делают непроверяемыми и затем централизованно обрабатывают через `@ControllerAdvice`.

## 2. `@ControllerAdvice`, `@ExceptionHandler`, `@Valid`

### `@ControllerAdvice`

`@ControllerAdvice` позволяет задать общую обработку ошибок сразу для всех контроллеров Spring MVC.

Он нужен для того, чтобы:

- не дублировать `try/catch` в каждом контроллере;
- возвращать единый формат ошибок;
- держать логику обработки ошибок в одном месте.

Если используется `@RestControllerAdvice`, ответ сразу возвращается в JSON.

### `@ExceptionHandler`

`@ExceptionHandler` указывает, какое исключение обрабатывает конкретный метод.

С его помощью можно:

- вернуть нужный HTTP-статус;
- сформировать понятный error-response;
- централизованно логировать ошибки.

### `@Valid`

`@Valid` запускает bean validation для объекта.

Чаще всего используется:

- на `@RequestBody`;
- на `@ModelAttribute`;
- на DTO и вложенных объектах.

### Как это работает вместе

1. Клиент отправляет запрос.
2. Spring создаёт объект DTO.
3. `@Valid` проверяет поля.
4. При ошибке выбрасывается исключение.
5. `@ControllerAdvice` перехватывает его и формирует единый ответ с ошибкой.

## 3. Логирование, уровни логирования, библиотеки, ротация

### Что такое логирование

Логирование — это запись информации о работе приложения.

Логи нужны, чтобы:

- понимать, что происходит в системе;
- искать ошибки;
- анализировать работу API;
- отслеживать производительность.

### Уровни логирования

- `TRACE` — очень подробные технические детали;
- `DEBUG` — информация для отладки;
- `INFO` — обычные рабочие события;
- `WARN` — подозрительные ситуации;
- `ERROR` — ошибки.

Обычно в production оставляют в основном `INFO`, `WARN` и `ERROR`.

### Основные библиотеки

- `SLF4J` — фасад, то есть единый API для логирования;
- `Logback` — популярная реализация, часто используется в Spring Boot по умолчанию;
- `Log4j2` — ещё одна известная реализация логирования.

### Ротация логов

Ротация логов — это автоматическое создание новых лог-файлов и архивирование старых.

Она нужна, чтобы:

- лог не рос бесконечно;
- диск не заполнялся;
- старые логи можно было хранить отдельно.

Ротацию обычно настраивают:

- по времени;
- по размеру;
- по времени и размеру одновременно.

## 4. AOP, Aspect, JoinPoint, Advice

### Что такое AOP

`AOP` (`Aspect-Oriented Programming`) — это подход, при котором сквозная логика выносится отдельно от бизнес-логики.

Примеры такой логики:

- логирование;
- безопасность;
- транзакции;
- аудит;
- измерение времени выполнения.

### Aspect

`Aspect` — это класс, в котором описана такая сквозная логика.

### JoinPoint

`JoinPoint` — это точка выполнения программы, куда можно встроить дополнительное поведение. В Spring AOP это обычно вызов метода.

### Advice

`Advice` — действие, которое выполняется относительно `JoinPoint`.

Основные виды:

- `@Before` — до метода;
- `@After` — после метода;
- `@AfterReturning` — после успешного завершения;
- `@AfterThrowing` — после исключения;
- `@Around` — вокруг метода.

`@Around` особенно удобен, когда нужно измерить время выполнения метода или залогировать и вход, и выход, и ошибку.

## 5. Логирование через AOP vs логирование в коде

### Логирование через AOP

Подходит для типовых вещей, которые повторяются во многих местах:

- время выполнения методов;
- общий аудит;
- одинаковое логирование входа и выхода.

Плюсы:

- меньше дублирования;
- не засоряет бизнес-код;
- проще поддерживать.

Минус: такая логика менее очевидна новичку, потому что она вынесена из метода.

### Логирование прямо в коде

Подходит для уникальных бизнес-событий:

- пользователь создан;
- операция отклонена;
- перевод выполнен.

Плюсы:

- логика видна прямо в методе;
- удобно писать специфичные сообщения.

Минусы:

- появляется дублирование;
- код становится перегруженным.

На практике обычно совмещают оба подхода.

## 6. Паттерны проектирования

### Что такое паттерн

Паттерн проектирования — это типовое решение часто встречающейся задачи проектирования.

Важно: паттерн — это не готовый код и не библиотека. Это общая идея, как правильно организовать классы и их взаимодействие.

### Для чего нужны паттерны

Паттерны нужны, чтобы:

- не изобретать одно и то же решение заново;
- строить код по понятным и проверенным схемам;
- уменьшать связанность между классами;
- упрощать расширение и поддержку проекта;
- быстрее понимать архитектуру чужого кода.

То есть паттерн нужен не "ради красоты", а ради более удобной, понятной и устойчивой структуры программы.

Например, если в проекте постоянно возникает одна и та же проблема, паттерн даёт уже известный способ решить её аккуратно и предсказуемо.

## 7. Типы паттернов. Минимум по одному каждого типа + Singleton

Паттерны обычно делят на три группы:

- порождающие;
- структурные;
- поведенческие.

### Порождающие паттерны

Они отвечают за создание объектов.

#### Singleton

`Singleton` гарантирует, что у класса будет только один экземпляр.

Пример:

- объект конфигурации;
- общий менеджер настроек;
- singleton-bean в Spring.

#### Factory Method

`Factory Method` выносит создание объекта в отдельный метод.

Он полезен, когда клиенту не нужно знать, какой конкретный класс создаётся.

### Структурные паттерны

Они отвечают за удобное соединение классов и объектов.

#### Adapter

`Adapter` позволяет связать несовместимые интерфейсы.

Пример: преобразование внешнего API в формат, удобный для внутреннего кода.

#### Facade

`Facade` даёт простой интерфейс к сложной подсистеме.

Пример: один сервис скрывает внутри несколько вызовов репозиториев, мапперов и проверок.

### Поведенческие паттерны

Они описывают взаимодействие объектов и распределение логики между ними.

#### Strategy

`Strategy` позволяет выбирать один из нескольких алгоритмов во время выполнения.

Пример: разные способы расчёта, сортировки или валидации.

#### Observer

`Observer` описывает ситуацию, когда один объект уведомляет другие объекты о событии.

Пример:

- listeners;
- подписки;
- обработчики событий.

### Краткий вывод

- порождающие паттерны отвечают за создание объектов;
- структурные — за организацию связей;
- поведенческие — за взаимодействие и поведение.

## 8. Рефакторинг

Рефакторинг — это улучшение внутренней структуры кода без изменения внешнего поведения программы.

Он нужен, чтобы:

- убрать дублирование;
- улучшить читаемость;
- упростить поддержку;
- подготовить код к дальнейшему развитию.

Примеры рефакторинга:

- вынесение повторяющегося кода в метод;
- переименование классов и методов;
- разделение большого класса на несколько;
- вынос обработки ошибок в `@ControllerAdvice`;
- вынос логирования времени в AOP-аспект.

Главная идея: при рефакторинге поведение системы должно остаться тем же, меняется только внутреннее устройство кода.
