# Теория к лабораторной работе 5

## 1. Bulk-операции

### Что такое bulk-операция

Bulk-операция — это операция, которая обрабатывает сразу набор объектов за один запрос.

Примеры:

- массовое создание записей;
- массовое обновление;
- массовое удаление;
- импорт данных из внешней системы.

### Зачем они нужны

Bulk-операции позволяют:

- уменьшить количество HTTP-запросов;
- сократить накладные расходы на сеть;
- обработать набор данных как единую бизнес-операцию;
- упростить импорт и миграцию данных.

### Какие есть риски

- запрос может быть слишком большим;
- сложнее контролировать частичные ошибки;
- важно определить поведение при сбое одного элемента;
- особенно важна транзакционность.

### Bulk в контексте REST

Чаще всего bulk-операция реализуется через `POST`, где в теле передаётся массив объектов.

Пример:

```json
[
  { "name": "item1" },
  { "name": "item2" }
]
```

Если операция должна быть атомарной, её обычно выполняют в транзакции.

## 2. Stream API и лямбды

### Что такое Stream API

`Stream API` — это механизм обработки последовательностей данных в декларативном стиле.

Он позволяет:

- фильтровать элементы;
- преобразовывать их;
- агрегировать;
- собирать в итоговую коллекцию.

### Что такое лямбда-выражение

Лямбда — это краткая форма записи анонимной функции.

Пример:

```java
item -> item.getName()
```

### Часто используемые операции

- `map()` — преобразование элементов;
- `filter()` — отбор по условию;
- `forEach()` — действие для каждого элемента;
- `sorted()` — сортировка;
- `toList()` / `collect(...)` — сбор результата.

### Пример

```java
List<String> names = users.stream()
        .map(User::getUsername)
        .toList();
```

Здесь:

- берётся список пользователей;
- из каждого объекта извлекается имя;
- создаётся новый список имён.

### Плюсы

- меньше шаблонного кода;
- лучше читается обработка коллекций;
- удобнее выражать цепочку преобразований.

## 3. Optional

### Что такое Optional

`Optional<T>` — это контейнер, который либо содержит значение, либо пуст.

Он используется для явной работы с ситуацией, когда значение может отсутствовать.

### Зачем нужен Optional

`Optional` помогает:

- уменьшить количество `null`-проверок;
- сделать код более выразительным;
- явно показать, что значение необязательно.

### Основные методы

- `of(...)` — создать `Optional` из непустого значения;
- `ofNullable(...)` — создать `Optional`, допускающий `null`;
- `map(...)` — преобразовать значение, если оно есть;
- `filter(...)` — оставить значение только при выполнении условия;
- `orElse(...)` — вернуть значение по умолчанию;
- `orElseThrow(...)` — выбросить исключение, если значения нет.

### Пример

```java
Budget budget = Optional.ofNullable(request.getBudgetId())
        .map(this::getBudget)
        .orElse(null);
```

### Когда использовать

`Optional` хорошо подходит:

- для результатов поиска;
- для необязательных полей;
- для цепочек безопасной обработки.

### Когда не стоит злоупотреблять

Не рекомендуется:

- делать `Optional` полем JPA-сущности;
- использовать его везде вместо обычных условий;
- усложнять код там, где обычный `if` читается лучше.

## 4. Пирамида тестирования и TDD

### Пирамида тестирования

Пирамида тестирования показывает, как обычно распределяют разные типы тестов.

Снизу вверх:

1. unit-тесты;
2. интеграционные тесты;
3. end-to-end тесты.

### Смысл пирамиды

Самыми многочисленными должны быть unit-тесты, потому что они:

- быстрые;
- дешёвые в поддержке;
- изолированно проверяют логику.

Интеграционных тестов обычно меньше, потому что они:

- запускаются дольше;
- требуют инфраструктуры;
- зависят от базы, Spring-контекста и внешних компонентов.

E2E-тестов обычно ещё меньше, потому что они самые дорогие и самые медленные.

### Что такое TDD

`TDD` (`Test-Driven Development`) — подход, при котором разработка идёт через тесты.

Классический цикл:

1. написать тест;
2. убедиться, что он падает;
3. написать минимальный код, чтобы тест прошёл;
4. выполнить рефакторинг.

Этот цикл часто называют:

- `Red`
- `Green`
- `Refactor`

### Что даёт TDD

- более продуманную архитектуру;
- меньшую связанность кода;
- уверенность при рефакторинге.

## 5. Unit-тесты и интеграционные тесты

### Unit-тесты

Unit-тест проверяет маленькую единицу логики изолированно.

Обычно это:

- один класс;
- один метод;
- одна бизнес-ветка.

Особенности:

- быстрый запуск;
- нет реальной базы данных;
- зависимости часто заменяются mock-объектами.

### Интеграционные тесты

Интеграционный тест проверяет совместную работу нескольких частей системы.

Например:

- сервис + репозиторий + база данных;
- контроллер + Spring MVC + сериализация JSON;
- приложение целиком с поднятым контекстом Spring.

### Главное различие

Unit-тест отвечает на вопрос:

- правильно ли работает логика конкретного класса?

Интеграционный тест отвечает на вопрос:

- правильно ли взаимодействуют реальные компоненты вместе?

### Что лучше использовать

Оба типа тестов нужны, но для повседневной проверки бизнес-логики чаще всего основной упор делают на unit-тесты.

## 6. JUnit и Mockito

### JUnit

`JUnit` — это основная библиотека для написания тестов в Java.

С её помощью можно:

- объявлять тестовые методы через `@Test`;
- выполнять подготовку через `@BeforeEach`;
- делать проверки через `assertEquals`, `assertThrows` и другие assertions.

Пример:

```java
@Test
void shouldThrowWhenRequestIsEmpty() {
    assertThrows(BadRequestException.class, () -> service.createBulkTx(List.of()));
}
```

### Mockito

`Mockito` — библиотека для создания mock-объектов.

Она позволяет:

- подменять зависимости;
- задавать ожидаемое поведение;
- проверять, как вызывались методы зависимостей.

Примеры:

```java
when(accountRepository.findById(1L)).thenReturn(Optional.of(account));
verify(transactionRepository, times(2)).save(any(Transaction.class));
```

### Почему JUnit и Mockito часто используют вместе

Связка `JUnit + Mockito` удобна для unit-тестов сервисного слоя:

- `JUnit` запускает тест и даёт assertions;
- `Mockito` изолирует сервис от репозиториев и других зависимостей.

Это позволяет проверять именно бизнес-логику, не поднимая всё приложение целиком.
